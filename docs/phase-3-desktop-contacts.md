# Phase 3 desktop contacts

The Avalonia contact screen mirrors the UWP master-detail layout: a keyboard-selectable list (photo thumbnail, display name, organization, favorite) and a detail editor with a separate edit snapshot, repeatable phone/email/address entries, photo selection and preview, favorite editing, a birthday date picker and social profiles. A view-header ribbon holds New, Delete, Import vCard, Export vCard and Save, plus the latest status message; long-running work drives the header's progress ring and success/failure icon. Older-data import is an explicit button below the editor. JSON export is no longer offered in the UI. The list is backed by the SQLite contact service. The editor copies child entries and photo bytes when opening a contact; changing one draft cannot mutate another persisted contact. It tracks unsaved changes: switching contacts or starting a new one asks before discarding them, and reloading the list keeps them. Deletion asks for confirmation and then selects the neighboring contact. A stored photo that cannot be previewed is kept as-is rather than blocking the contact from opening. Birthdays are stored as ISO `yyyy-MM-dd` calendar dates; the picker's time and offset are discarded so the date never shifts, and unparseable values (such as yearless dates) are left unchanged until edited. Search filtering exists in the view model but has no search box yet. The theme follows the OS by default and can be changed in Settings for the current session.

The existing Avalonia controls and the already referenced `Avalonia.Controls.DataGrid` package are sufficient; no additional UI control package is introduced. Picker calls stay in View code-behind and pass a selected path or stream into the ViewModel. The older-data picker accepts the two supported legacy filenames; the import service backs up before writing. If two legacy sources overlap, import one at a time after comparing them. A change to a legacy file after import is reported as `ChangedSource` and not merged automatically.

## vCard boundary

The `VCardContactService` writes vCard 3.0, including CRLF line endings, UTF-8 folding at 75 octets, escaped text, multiple phones/emails/addresses, phonetic name extensions, social profiles (`X-SOCIALPROFILE` for X/Twitter, Facebook and LinkedIn), favorites as the `starred` category, ISO birthdays, and JPEG/PNG photo bytes. It accepts common vCard 3.0/4.0 text fields and base64/data URI photos. Labels come from the first descriptive `TYPE` value, skipping capability values such as `INTERNET`, `VOICE` and `PREF`. Other categories are kept alongside `starred`. It retains otherwise unmapped single-line properties through SQLite for subsequent export.

Identity follows the vCard `UID`. A GUID UID (including `urn:uuid:`) becomes the contact ID; any other UID maps to a stable hash-derived ID. Exports add `UID:urn:uuid:<id>` when a contact has none, so re-importing an export or the same external file updates existing contacts instead of duplicating them. Cards without a UID are always added as new contacts. An import is saved in a single transaction: if any card is invalid, no contacts change. When an import updates the selected contact, the editor reloads it unless it has unsaved changes.

This is deliberately a narrow interchange implementation. It rejects quoted-printable vCard data, non-3.0/4.0 versions and unsupported encodings rather than silently misreading them. Photo URLs (as in Google Contacts exports), undecodable photos and image formats other than JPEG/PNG are skipped without failing the import. The maintained MIT-licensed [FolkerKinzel.VCards](https://github.com/FolkerKinzel/VCards) library supports broader version coverage and is a candidate if real-device samples require it. The current adapter needs actual Android/iOS round-trip verification before the vCard gate is closed.

The Phase 3 feature gate remains open until the desktop UI and external vCard round-trip have been tested on target systems. `docs/roadmap.md` retains the Store update gate for Phase 5.
